# AGENTS.md

## Назначение

Этот документ задает правила разработки для проекта `sadmoneyapp`.
Проект модульный, кроссплатформенный (`Windows` + `macOS`), состоит из:

- frontend: `React + TypeScript + Vite` в `src/`
- backend/native layer: `Tauri + Rust` в `src-tauri/`

Цель правил: ускорять безопасные правки, не раздувать область изменений и поддерживать предсказуемую архитектуру.

## Базовые принципы работы

- Не сканировать кодовую базу целиком без необходимости.
- При любой правке сначала искать только узкое место: конкретный экран, компонент, хук, модуль, команду Tauri, модель или слой хранения, который относится к задаче.
- Расширять область чтения только если локальный контекст недостаточен для безопасной правки.
- Не делать широких рефакторингов вместе с функциональной задачей без явной необходимости.
- Любое изменение должно быть минимальным по радиусу воздействия и понятным по причине.
- Предпочитать модульные изменения, а не “быстрые” правки, размазанные по всему проекту.
- Если подходящий метод, функция, хук, утилита или команда уже существует, переиспользовать их вместо дублирования логики.

## Правило узкого поиска

Перед изменением кода придерживаться такого порядка:

1. Найти точку входа пользовательского сценария.
2. Найти модуль, который владеет логикой этого сценария.
3. Проверить связанные типы, утилиты и зависимости только в соседнем контексте.
4. Идти глубже в другие модули только если без этого нельзя проверить корректность изменения.

Практически это значит:

- для UI-задач начинать с `src/App.tsx`, нужного компонента в `src/components/`, связанных хуков в `src/hooks/` и утилит в `src/lib/`
- для backend-задач начинать с `src-tauri/src/commands.rs`, затем смотреть `models.rs`, `storage.rs`, `lib.rs`
- не читать подряд все файлы проекта “для понимания архитектуры”, если задача локальная

## Кодировка и текстовые файлы

- Все текстовые файлы проекта создавать и сохранять в кодировке `UTF-8`.
- Предпочтительно использовать `UTF-8` без BOM, если инструмент не требует иного.
- Не смешивать разные кодировки в репозитории.
- Новые файлы и правки должны сохранять корректное отображение кириллицы и специальных символов на `Windows` и `macOS`.
- Предпочитать `LF`, если конкретный инструмент или экосистема не требует иного.

## Кроссплатформенность: Windows и macOS

- Не хардкодить платформозависимые пути, разделители путей или системные директории.
- В frontend использовать API путей Tauri вместо ручной сборки строк путей, когда работа идет с файловой системой.
- В Rust и TypeScript не предполагать одинаковое поведение регистра файловой системы, путей, временных директорий и прав доступа.
- Не опираться на `~/...`, `%APPDATA%`, `C:\\...` или `/Users/...` напрямую в прикладной логике.
- Любая файловая операция должна учитывать, что системные директории на `Windows` и `macOS` различаются.
- Имена файлов, экспортов и импортов должны быть согласованы по регистру, чтобы код одинаково собирался на разных ОС.
- Не использовать shell-специфичные команды или допущения в рантайм-логике приложения.
- Если поведение платформ различается, различие должно быть явно локализовано в одном модуле или адаптере.

## Модульная архитектура

- Каждый модуль должен иметь одну понятную зону ответственности.
- UI-компоненты не должны владеть бизнес-правилами, если эти правила можно вынести в `hooks` или `lib`.
- Общие вычисления, форматирование, money/date/category-логику выносить в `src/lib/`.
- Повторно используемое поведение UI выносить в `src/hooks/`.
- Tauri-команды должны быть тонким boundary-слоем между frontend и Rust-логикой.
- Модели данных и хранение должны быть отделены от слоя команд.
- Межмодульные зависимости должны быть направлены от частного к общему, а не создавать циклы.
- Если модуль начинает решать несколько задач сразу, его нужно разделить до появления нового сильного сцепления.
- Перед добавлением нового метода или функции сначала проверять, можно ли безопасно переиспользовать существующую реализацию без ухудшения читаемости и ответственности модуля.

## Правила для frontend-разработки

- Компоненты должны быть небольшими и ориентированными на один пользовательский сценарий.
- Состояние хранить как можно ближе к месту использования, но без дублирования одних и тех же данных в нескольких местах.
- Не хранить в state то, что можно надежно вычислить из props, route, server/native data или другого state.
- Избегать противоречивого, избыточного и глубоко вложенного state.
- Предпочитать явные типы `TypeScript`; не ослаблять типизацию без причины.
- Держать границы между presentational UI, hooks и domain utilities явными.
- Не смешивать форматирование данных, побочные эффекты и JSX-рендеринг в одном громоздком блоке.
- Эффекты должны быть минимальными и только для синхронизации с внешним миром; вычисления делать вне `useEffect`, если это возможно.
- Обработчики ошибок, пустые состояния, loading-состояния и состояния отсутствия данных должны быть продуманы явно.
- Формы должны быть предсказуемыми: валидировать ввод, не терять пользовательские данные, не ломать навигацию с клавиатуры.
- Использовать семантический HTML там, где это возможно, а не заменять его `div`-конструкциями.
- Все интерактивные элементы должны быть доступны с клавиатуры и иметь заметный `focus` state.
- У каждого поля формы должны быть корректные подписи, а у кнопок и иконок понятные названия.
- Не создавать лишние перерисовки из-за неправильной структуры state или неявных зависимостей.
- Стили не должны ломать читаемость, контрастность, фокус и адаптивность интерфейса.
- Адаптивность считать обязательной: интерфейс должен быть usable на типичных desktop-размерах и небольших окнах.
- При добавлении нового UI сохранять визуальную и поведенческую консистентность проекта.

## Правила для backend / Tauri / Rust

- Tauri-команды должны быть узкими, явными и ограниченными по ответственности.
- Каждая команда должна валидировать входные данные на boundary-слое.
- Нельзя передавать на frontend внутренние ошибки, стеки или чувствительные детали реализации.
- Операции чтения/записи должны быть по возможности атомарными и устойчивыми к частичным сбоям.
- Модели данных должны быть стабильными, предсказуемыми и сериализуемыми без двусмысленности.
- Вся логика работы с хранилищем должна быть централизована, а не размазана по разным командам.
- Ошибки должны быть типизированы или хотя бы нормализованы в понятные сообщения и коды поведения.
- Не делать скрытых сайд-эффектов в командах, которые по имени выглядят как чтение.
- При изменении схемы данных продумывать обратную совместимость и миграционный путь.
- Не доверять данным с frontend даже в desktop-приложении: валидировать, ограничивать и санитизировать вход.
- Правила доступа Tauri capabilities задавать по минимально необходимому принципу.
- Новые разрешения, filesystem scope и window capabilities не добавлять “про запас”.
- Платформенные различия, filesystem-пути и системные интеграции изолировать в одном слое.

## Безопасность и best practices

- Следовать принципу least privilege для Tauri permissions, capabilities и системных API.
- Использовать только `HTTPS` для внешних сетевых взаимодействий приложения, если такие появятся.
- Валидировать формат входящих данных до бизнес-обработки.
- Не логировать секреты, токены, приватные ключи, чувствительные персональные или финансовые данные.
- Ошибки для пользователя должны быть безопасными и понятными, а диагностические детали оставаться во внутреннем логе.
- Если ввод влияет на файловую систему, команды ОС, URL или сериализацию, его нужно отдельно проверять.
- Любые зависимости и новые плагины подключать только при реальной необходимости.

## Производительность и поддерживаемость

- Сначала исправлять узкие места, подтвержденные задачей, а не оптимизировать все подряд.
- Не добавлять абстракции “на будущее”, если они не уменьшают текущую сложность.
- Избегать дублирования логики между компонентами, хуками и Rust-командами.
- Если логика уже реализована в одном месте и подходит по ответственности, расширять или переиспользовать ее вместо создания почти одинаковых методов.
- Публичные интерфейсы модулей должны быть маленькими и стабильными.
- Сложные вычисления и преобразования данных должны быть вынесены из UI-слоя.
- Любая новая сущность должна иметь понятное имя, отражающее предметную область, а не техническую случайность.

## Проверка изменений

- Перед завершением правки проверить, что изменение локально согласовано с соседними модулями, а не только с редактируемым файлом.
- Для frontend-правок проверить типы, сборку и базовую работоспособность UI-сценария.
- Для backend/Tauri-правок проверить сериализацию, обработку ошибок и кроссплатформенные допущения.
- Если задача затрагивает пути, файлы, окна, capabilities или внешние процессы, отдельно проверить сценарий на `Windows` и `macOS` хотя бы на уровне кода и допущений.

## Локальный запуск

- Для локального dev-запуска desktop-приложения использовать `npm run tauri dev`.
- Не поднимать только `npm run dev`, если нужно проверить поведение именно Tauri-приложения, окно, native layer или интеграции с файловой системой.
- Если перед запуском `npm run tauri dev` уже работает отдельный `vite`-сервер, его нужно остановить, чтобы избежать конфликта портов.

## Что считать хорошей правкой

Хорошая правка в этом проекте:

- решает конкретную задачу без лишнего обхода всего репозитория
- меняет минимально необходимое число модулей
- сохраняет модульные границы
- не ломает кроссплатформенность
- остается типобезопасной и читаемой
- не ослабляет безопасность Tauri и пользовательских данных
- оставляет кодовую базу чуть понятнее, чем была до изменения
